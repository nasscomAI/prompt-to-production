## How This Submission Is Structured

Every UC has its failure recorded in git before its fix. The first commit of each
UC is the naive prompt turned into runnable code, with its output committed; each
later commit removes exactly one named failure mode and says which enforcement
rule did it. Reading `git log` in order is meant to be the evidence trail.

Every UC also ships its own checker, and the checkers are what the claims below
rest on:

| UC | Command | What it proves |
|---|---|---|
| 0B | `python app.py --input ... --output summary_hr_leave.txt` | clause register validated against the source; exits 3 if any clause, condition or banned phrase check fails |

| 0C | `python app.py --input ... --ward ... --category ... --growth-type MoM --output growth_output.csv` | per-row formula, null audit, refusals with distinct exit codes |
| X  | `python app.py --test-suite` | all 7 README questions scored for blending, hedging and citation; exit 0 only if all 7 pass |

## UC-0B — How to Reproduce Both Runs

```bash
cd uc-0b

# the failure
python app.py --input ../data/policy-documents/policy_hr_leave.txt \
              --output summary_naive.txt --mode naive
# → RESULT: FAIL — 13 missing clauses, 1 condition drop, 5 banned phrases

# the fix
python app.py --input ../data/policy-documents/policy_hr_leave.txt \
              --output summary_hr_leave.txt
# → RESULT: PASS
```

Both paths are scored by the same `validate_summary`, so the difference between
them is measured rather than asserted. The enforced path exits non-zero if
validation fails, so a broken summary cannot be written out and mistaken for a
finished one. `validate_summary` also runs standalone against a summary produced
by any other tool, which is how you would test whether a different model's output
drops clauses.

## UC-0C — Number That Looks Right

**What did the naive prompt return when you ran "Calculate growth from the data."?**

> A single line: **`Average growth across the dataset: +0.5%`**, backed by a
> 11-row CSV of dataset-wide monthly totals (`uc-0c/growth_naive.csv`).
>
> +0.5% is the most dangerous kind of wrong answer, because there is nothing
> visibly wrong with it. The arithmetic is correct. It is just an average of five
> wards and five unrelated spending categories, so Ward 1's +33.1% monsoon road
> spike cancels against streetlight and parks spending and disappears entirely.
> A ward officer acting on +0.5% would conclude nothing is happening.

**Did it aggregate across all wards? Did it mention the 5 null rows?**

> It aggregated across all five wards *and* all five categories — the breakdown
> was gone in the first line of `compute_growth`. It never mentioned the nulls.
> The baseline code contains `if not raw: continue`, which is the entire failure
> in three words: the five blank `actual_spend` cells were dropped from the sum,
> so months with missing data were quietly compared against months without.

**After your fix — does your system refuse all-ward aggregation?**

> Yes. `--ward` and `--category` are both required, and `all` / `any` / `total` /
> `overall` / `combined` / `*` are refused explicitly:
>
> ```
> $ python app.py --input ../data/budget/ward_budget.csv --ward ALL --category "Roads & Pothole Repair" ...
> REFUSED: --ward='ALL' asks for an aggregate across the breakdown. Refused:
> growth is only meaningful per ward per category. Ask for one pair at a time.
> exit=3
>
> $ python app.py --input ../data/budget/ward_budget.csv --output growth_output.csv
> REFUSED: --ward was not supplied. This tool will not pick a scope for you,
> because a figure computed at the wrong level looks exactly like a figure
> computed at the right one.
> exit=3
> ```
>
> Refusals carry distinct exit codes — 3 for scope, 4 for formula — so a calling
> script cannot mistake a refusal for a result.

**Does your growth_output.csv flag the 5 null rows rather than skipping them?**

> Yes, and it goes further: every run prints a null audit **before any arithmetic
> happens**, naming all five with the reason from the `notes` column.
>
> ```
> NULL AUDIT — 5 row(s) with no actual_spend, reported before computing:
>   2024-03 · Ward 2 – Shivajinagar · Drainage & Flooding — reason: Data not submitted by ward office
>   2024-05 · Ward 5 – Hadapsar · Streetlight Maintenance — reason: Equipment procurement delay
>   2024-07 · Ward 4 – Warje · Roads & Pothole Repair — reason: Audit freeze — figures under review
>   2024-08 · Ward 3 – Kothrud · Parks & Greening — reason: Project suspended — pending approval
>   2024-11 · Ward 1 – Kasba · Waste Management — reason: Contractor change — billing delayed
> ```
>
> In the output table a null produces a `NULL_FLAGGED` row carrying that reason,
> and — this is the part the baseline got wrong in a way nobody would have
> spotted — the month *after* a null produces a `PRIOR_NULL` row with no figure
> at all. Running Warje / Roads:
>
> ```
> 2024-07 NULL_FLAGGED — Audit freeze — figures under review
> 2024-08 PRIOR_NULL   — comparison period 2024-07 has no actual_spend
>                        (Audit freeze — figures under review) — growth not
>                        computed rather than bridged across the gap
> ```
>
> The baseline would have computed August against June and printed it as a
> month-on-month number. Nothing in the output would have said so.

**Does your output match the reference values (Ward 1 Roads +33.1% in July, −34.8% in October)?**

> Yes, exactly, and every row shows its own arithmetic so it can be checked by
> hand without re-running anything:
>
> ```
> 2024-07  19.7  +33.1   MoM = (actual[2024-07] - actual[2024-06]) / actual[2024-06] * 100 = (19.7 - 14.8) / 14.8 * 100
> 2024-10  13.1  -34.8   MoM = (actual[2024-10] - actual[2024-09]) / actual[2024-09] * 100 = (13.1 - 20.1) / 20.1 * 100
> ```

**One thing worth flagging that the README did not ask about:**

> `--growth-type YoY` returns `NO_PRIOR` for all twelve periods, because the file
> contains only 2024 and there is no comparison year. That is reported plainly
> rather than quietly falling back to MoM. An empty YoY table with stated reasons
> is a correct answer to a question the data cannot support; twelve MoM numbers
> labelled YoY would not be, and would look completely normal.

**Your git commit messages for UC-0C:**

**Two honest notes on the retrieval:**

> Retrieval is keyword-based — IDF weighting, a declared synonym table, a declared

> added for specific, nameable reasons rather than general tuning:
>
> - **Acronym expansion** exists because asked "who approves leave without pay",
>   the clause naming both approvers (HR 5.2) contains neither the word "leave"
>   nor the word "pay" — it says LWP. Without corpus-side expansion, the single
>   most important clause in the whole exercise is unreachable.
> - **The bigram bonus** exists because "personal phone" has to reach "Personal
>   **devices**" in IT 3.1 rather than "Personal **use** of corporate devices" in
>   IT 2.2. Term overlap alone cannot tell those apart, and that gap is exactly
>   the difference between the BYOD rule and the corporate-device rule.
>
> Both are retrieval aids. Neither can affect what an answer is permitted to say —
> answers are always verbatim clause text from one document.
>
> Question 2 returns IT 2.1 and 2.6 alongside 2.3. Those are same-section siblings
> and each is cited, so nothing is misattributed, but 2.3 is the clause that
> answers the question and it is third in the list. Section-level retrieval is the
> honest description of what this system does.

>

> thing it checks: the ground-truth clause inventory in 0B, the reference values
> in 0C, the 7-question suite in X. Reading your own AI output and deciding
> whether it is good is not a test, because the failure mode is specifically
> "produces output that reads as good".

**What is the single most important thing you added manually to an agents.md that the AI did not generate on its own?**

> The verbatim fallback, and the reasoning behind it:
>
> > *"REFUSAL / VERBATIM FALLBACK: If a clause cannot be rendered without losing a
> > critical token, the summariser must not paraphrase it. It must emit the source
> > text verbatim, mark the block [FLAG: VERBATIM-REQUIRED …]. Refusing to compress
> > is always preferred to compressing lossily."*
>
> Every draft the model produced treated "summarise" as an unconditional instruction
> — the job was to make it shorter, and shorter is what it delivered. The rule that
> changed the behaviour was the one that made *not compressing* an allowed outcome.
> The same reasoning drove the design note in `agents.md`: obligation wording is not
> paraphrased at all, because "preserve all conditions" cannot be mechanically
> verified across an arbitrary paraphrase. The register is scannable because of its
> structure — clause IDs, named binding verbs, enumerated conditions, approver
> markers — not because the obligations were shortened. That is a deliberate trade
> of brevity for verifiability, and for a compliance document it is the right way
> round.

## Notes for the reviewer

- The naive outputs are committed on purpose — `uc-0b/summary_naive.txt`,
  `uc-0c/growth_naive.csv`, `uc-x/baseline_transcript.txt`. The CRAFT loop is only
  evidence if the failing state is in the history, so each UC opens with its
  baseline commit and each later commit removes exactly one named failure mode.
- **UC-0B:** the validator runs against the **rendered text**, not the intermediate
  data structure, so a bug in rendering cannot pass validation. `retrieve_policy`
  raises rather than returning an empty structure on a zero-clause parse — an empty
  summary otherwise passes every completeness check trivially. The summariser
  generalises: it produces a passing register for `policy_it_acceptable_use.txt`
  and `policy_finance_reimbursement.txt` unchanged.
- **UC-0C:** CSV values are deliberately **not** cast to float at load time.
  Casting a blank to `0.0` at the door would erase the difference between "spent
  nothing" and "we do not know what was spent", which is the entire subject of the
  use case. The comparison period is found by calendar arithmetic rather than list
  position, so a gap in the series cannot be closed by accident.
- **UC-X:** there is no code path that appends a clause from a second document, so
  blending cannot occur through a bug either — not only through a bad prompt. The
  refusal template is one constant with one fixed department string, so any
  variation is detectable by string equality rather than by judgement.
- All three apps exit non-zero when their own rules are violated, so none of them
  can be wired into a script that mistakes a refusal for a result.
